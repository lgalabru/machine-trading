# machine-trading 0.9.0: design

0.8.0 closed the leaks its exploit checks caught, but four weaknesses remain:

- **Market-making grades don't replay.** The grader's maker races the bot in real
  time. The same reference made $19.6 in calibration and $49 in the Harbor check.
- **Rewards are unreadable.** They are normalized by a hindsight bound no bot
  approaches, so the reference scores 0.01–0.04 and model scores sit in the
  same narrow band.
- **The hidden scenarios ship with the task.** By our own READMEs, the public
  version is a development benchmark.
- **Nothing says whether the task ranks strategies the way a trader would**, or
  how far the reference sits from the best honest play. The exploit checks
  only bound the bots above it.

0.9.0 fixes these and applies the skill's new design record and ladder
(`skills/trading-task-design/references/design-record.md`,
`ladder-and-ceilings.md`). It's ordered so each phase ships on its own.

## Phase 1: measurement (no change to what bots see)

### 1.1 Fresh hidden sets drawn in the verifier

- `task.toml` passes `MTH_EVAL_SEED` to the verifier from the host
  (`[verifier.env] MTH_EVAL_SEED = "${MTH_EVAL_SEED:-}"`).
- `test.sh` draws the scored set from it with `mth scenario generate`, stratified
  as today (18 crashes / 18 squeezes; 3 calm / 6 jumps / 3 trends). It writes
  only the seed's hash to the report.
- **Without a seed the verifier refuses to grade** (exit non-zero, no reward),
  and `tests/scenarios` is gone from the task.
- `just bench` draws one secret per batch (`python3 secrets`, never printed),
  keeps it in `jobs/<batch>/.seed` (mode 600, gitignored) so void trials can be
  re-run, and greps every job file for it afterwards.

### 1.2 The reference runs next to the bot

Fresh draws mean no precomputed reference PnL. The verifier grades the
reference (and the nop, as a health check) on the same sessions, in parallel
lanes (`mth grade --jobs`). The reference and nop are anchors: if one crashes
or overruns, the grade is void, never a score.

The cost is about 2× verifier time on flash-crash. Phase 3's lockstep world
removes the real-time wait, so it pays this back.

### 1.3 The reward

- **Keep the bound as the reward's denominator.** The exploit bots reach 2.6×
  and 11× the reference, so the reference is far from optimal. A
  reference-normalized reward would saturate, as it did in 0.6.0 and 0.7.0.
- **Report the reference-scaled score as the headline**: `skill = Σ(bot − nop) / Σ(reference − nop)`,
  unclamped. The reference scores 1, the nop 0, and a breach voids. Bench
  tables show `skill` with its interval; `reward` stays the Harbor metric.
- **Revisit once the ceilings exist (1.5).** If the regime oracle sits within
  ~1.3× the reference, switch the reward to its clamped reference-scaled form.

### 1.4 The ladder gate (`just ladder <task>`)

`just ladder` replaces `exploit-checks`. It grades a fixed set of bots, the
rungs, on F fresh secret sets (default 4), then checks an order rule written
per task in `bench/checks/ladder/<task>.toml`.

**Flash-crash rungs:**

| Rung | Expected | Notes |
| --- | --- | --- |
| nop | 0 | |
| blind short at the open, blind long at the open | ≈ 0, negative tail | the mirror family makes both coin flips |
| dip-buyer (`bots/dip-buyer`) | < 0 | buys every drop; squeezes and non-recoveries punish it |
| momentum (rides the first gap) | between the dip-buyer and the reference | |
| reference | 1 | |
| `flash-crash-opus`, `flash-crash-fable` | 1–3 | frozen 0.6.0 exploit bots |
| regime oracle | > every rung but hindsight | 1.5 |
| hindsight | top | the bound |

Order rule: `dip-buyer < momentum < reference < regime oracle < hindsight`,
`max(blind short, blind long) < reference`.

**Market-making rungs:** nop; a naive symmetric quoter one tick inside;
the same with skew; the reference; `market-making-opus` and
`market-making-fable`; the regime oracle; hindsight. Order rule:
`naive < skew-only < reference < regime oracle`.

**The checks:**

- The rule holds on every set. A bootstrap over per-regime pools estimates the
  per-set probability, which must be at least 0.85.
- The exploit bots keep 0.8.0's limits (at least 25% / 10% losing sessions,
  flash-crash at most 3× the reference).
- The reference is positive in every regime.

### 1.5 Ceilings

- **Regime oracle**, per task: a grader-only bot that receives the
  scenario's family draw (direction, legs, depth and timing for flash-crash;
  jump times and informed bursts for market-making), but not the path's noise.
  It plans with the reference's logic, parameterized by the truth. It runs
  only in `just ladder`, never in a task image. Its gap above the reference is
  what reading the market better can still earn. Report it by regime.
- **Hindsight** stays the bound.
- **A Bayes bot** (a particle filter over the generator) waits for 0.10. It's
  the most expensive and needs the lockstep world to be practical.

### 1.6 Bench reporting

- **Intervals.** `just bench-report <batch>` computes 90% bootstrap intervals
  over sessions (shared across models) and runs, for `skill` and `reward`,
  and lists which model gaps it doesn't resolve.
- **A pinned harness:**
  - the claude-code version;
  - `disallowed_tools=WebSearch,WebFetch,RemoteTrigger,PushNotification,CronCreate,CronDelete,SendMessage,ListAgents`;
  - `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, `ENABLE_TOOL_SEARCH=false`;
  - reasoning effort recorded per model.
- **Time limits.** The bench runs at the task's agent timeout (1 h) and a
  2-hour variant (`--agent-timeout-multiplier 2`), reported separately. Every
  score is quoted with its limit.
- **Void, not zero.** A trial with no reward, or a void grade (an anchor
  failed, the host was starved and `late_slots` went past a threshold), is
  re-run.
- **Committed results.** Each release's results go to
  `bench/results/<version>/`: per-trial `result.json`, per-session PnL,
  the bot source, and `scores.csv`. Transcripts stay in `jobs/`.

## Phase 2: design records and a leak audit

- **Write `bench/tasks/<task>/DESIGN.md` for both tasks**, to the skill's
  template:
  - the expert research;
  - the central decision and the options that look defensible;
  - a variants table (each regime's best response) and a habit-fails-where table;
  - a levers table with how an honest operator detects each lever;
  - the no-tells audit;
  - detectability in sd for each signal;
  - penalty twins;
  - the generation log, 0.3.0 → 0.8.0 (each leak and what closed it), which
    today lives across the changelog and memory.
- **`just leak-audit <task>`**: grep the agent image and every agent-visible
  file for the generator's mechanic names, taken from the family structs
  (`gap_odds`, `fizzle_*`, `informed_odds`, `fakeouts`, `react_slots`, …).
  The instruction discloses ranges in plain words; a field name in it means
  generator internals leaked.
- **Detectability measurements**, from `mth scenario generate` at the scored
  mix:
  - flash-crash: how many slots after a gap a fizzle and a real leg can be
    told apart, in sd;
  - market-making: how well an informed burst separates from noise on the
    tape before the jump, and a fakeout's footprint against a real one.

  Targets: 1–4 sd within the window a bot has to act.

## Phase 3: a lockstep world (changes the bot contract)

This is what makes market-making grades replay, and it speeds up grading.

### Protocol `mth-turn-1`

- **Hello.** Before the first step the grader sends a hello with the mandate,
  the market, the clock (`steps`, `slots_per_step`) and the turn budget. The
  bot answers `ready`.
- **Steps.**
  - The grader pauses the surfnet's clock. For each step k it applies the
    scenario's waypoint, runs the takers' and the competitor's transactions
    for block k, and advances the clock.
  - It then sends the bot `{"t":"step","k","slot","oracle_usd","tape":[…],"fills":[…]}`
    on fd 3: the block's trades in execution order, with the bot's own
    marked.
  - The bot reads the chain over RPC as today, sends its transactions, and
    answers `done`. Its transactions land at the start of block k+1, before
    the takers.
- **Budget.** 3 s of CPU per turn, a 10 s wall cap and a hard stop at 30 s.
  What a bot sends after the cap is dropped.

### Consequences

- **botkit gains `Bot::on_step`.** `Trader` stays as is for RPC and orders.
  The starter, the reference, the maker and the dip-buyer port to it. Agent
  bots written against 0.8.0's polling loop break, which is acceptable for a
  minor version before 1.0.
- **Grades replay.** The competitor reads the book at a step boundary, never
  mid-race. The same bot on the same scenario gives the same PnL, and the
  oracle check can require it to the cent.
- **Sessions run as fast as the bot answers.** With the clock paused, a
  640-slot session takes as long as its turns, not 640 × 400 ms. Flash-crash's
  36 sessions with the reference alongside should fit well under today's 90
  minutes, so the hidden set can grow (48 or more) for more statistical
  power.
- **The realism cost.** There's no latency race inside a block: a bot that is
  faster in wall-clock time gains nothing. That's the price of determinism.
  The README's realism limits say so.

### The Surfpool dependency

Our cheatcode lockout disables methods for good, and the sneaky check proves
a bot can't call them on the surfnet's port. The grader now needs to pause
and advance the clock after lockout. Two options in `surfpool-ofm`:

- **(a)** An admin token: methods called with it bypass lockout, and the token
  is held only by the grader.
- **(b)** Manual block production, with an advance method on a unix socket
  the bot user can't open.

(b) keeps the RPC port's surface unchanged; (a) is less code. Either needs
your call, as Surfpool's owner.

## Phase 4: new levers (after the ladder exists to judge them)

**Market-making: a stale-quote sniper.**

- When the oracle moves by more than a threshold, a grader-run taker hits any
  resting quote still on the wrong side of the new level, sized to the quote.
  It acts in the block after the move. A bot that requotes on the step it sees
  the move is safe; one that requotes on a timer is picked off.
- This is real toxic flow. It's deterministic only in the lockstep world, so
  it comes after phase 3.
- **Its control pair**: the reference against the same bot requoting every
  4 steps.

**Market-making: a pace predator.**

- It learns the bot's requote rhythm and quote sizes, and front-runs the
  bot's predictable side when it's leaning.
- Hold this until the sniper's results are in; one new lever per generation
  keeps the ladder readable.

**Flash-crash: liquidity that withdraws.**

- The grader runs a maker (as in market-making), present in every session.
  It quotes around the splines in calm, and pulls back to the splines,
  widening, for a few steps after each gap.
- Taking into the shock costs more; resting entries and patience pay.
- **Its control pair**: the reference entering with resting orders against
  the same entries sent as market orders.

Each new lever goes through the levers table (how an honest operator detects
it), the no-tells audit (the maker is onboarded in every session), and the
ladder before it ships.

## Not in 0.9.0

- **Network faults** (expired blockhashes, dropped sends, 429s). They're
  cheap in the lockstep world; 0.10.
- **An arena** (several agent bots in one market). It needs lockstep and a
  stable ladder first.
- **A third task.** Breadth after measurement.

## As built (2026-10-31)

- **Clock control needed no Surfpool change.** The grader runs Surfpool
  in-process, and the SDK's `send_command` switches it to manual block
  production and produces each block (`SlotForward`), with no RPC at all.
  The admin token wasn't needed for that.
- **A Surfpool change was needed for a different reason:** standard methods
  still answered on the surfnet's own port, which a bot can reach, so in a
  lockstep world it could send while the world moves. The local branch
  `feat/secret-path` (on Surfpool `main`) serves RPC only at a secret path;
  the guard holds the bot's sends to its turn. Not pushed yet.
- **Executed is final.** Surfpool reports no status for a transaction that
  executed after the last block, so clients waiting for `confirmed` would
  wait out their turn. The guard serves reads at `processed` and finds such
  transactions with `getTransaction`.
- **Market-making has no regime oracle yet** (see
  `bench/checks/ladder/README.md`). Phase 4's levers (the stale-quote
  sniper, the pace predator, liquidity that withdraws) aren't built: they
  wait for the ladder's first results.

## Decisions (2026-10-30)

1. **Everything ships in 0.9.0**, lockstep included.
2. **Clock control after lockout: an admin token.** Cheatcodes called with a
   grader-held token bypass the lockout; the token never reaches the bot's
   environment.
3. **The secret is mandatory.** The verifier refuses to grade without
   `MTH_EVAL_SEED`; practice scenarios stay public in `environment/practice`.
4. **Bench reports headline `skill`** (reference = 1, unclamped) with
   intervals; `reward` stays Harbor's metric.

## Order of work for phases 1–2

1. `MTH_EVAL_SEED`, in-verifier draws, the public fallback, and the
   reference and nop graded in the verifier. Harbor checks on both tasks.
2. The ladder bots (blind short and long, momentum, naive and skew-only
   quoters) and `just ladder` with the order rules. This replaces
   `exploit-checks`.
3. The regime oracles for both tasks, and ceilings by regime.
4. `bench-report` with intervals, the pinned harness, and committed results.
5. The two design records, `leak-audit`, and the detectability numbers.
6. Release 0.9.0, then bench it at 1 h and 2 h.
